# Code Review последних изменений (1C EDT)

Второй слой поверх штатного статического анализатора EDT. Задача — находить то, что правилом не закодируешь: смысловые проблемы, антипаттерны, потенциальные баги. **Не помечай то, что уже ловит штатный статический анализатор EDT или форматтер** — только то, что вне их охвата. Для файлов с локальной историей находка обязана сидеть на изменённой строке; для новых файлов (без локальной истории) изменёнными считаются все строки файла.

Изменения определяются по локальной истории IDE (Eclipse local history), а не по git — скилл работает и в проектах без git-репозитория. `current` в этих тулах — живое состояние файла (включая несохранённые изменения редактора), `latest` — последняя ревизия локальной истории.

## Входные параметры

| Параметр | Описание |
|----------|----------|
| `${project_name}` | Имя проекта в EDT |
| `${relative_file_path}` | Путь к файлу относительно проекта |
| `${absolute_file_path}` | Абсолютный путь к файлу для ревью |

## Препроцессинг
!tool('deletemarkers')

## Порядок работы

Для получения данных используй **только** тулы из этого скилла: `localhistory`, `localchanges`, `read`, `setmarkers`. Не используй git, jgit или другие инструменты, не обращайся к файловой системе в обход `read`, не используй `getmarkers`.

### Шаг 1 — Определить статус файла

Вызови `localhistory` (аналог `git status`; запись с index 0 — текущее состояние файла):

```
project_name: ${project_name}
file_path: ${relative_file_path}
```

**Обработка статуса:**

1. **Новый файл** — `differs_from_latest` равен `null` (в `entries` нет ни одной записи, кроме `current`): локальной истории ещё нет. Пропустить Шаг 2 (diff не нужен), в Шаге 3 прочитать файл целиком и ревьюить как «всё добавлено».
2. **`differs_from_latest` = false** — текущее содержимое совпадает с последней ревизией истории: изменений нет, **немедленно завершить работу, маркеры не трогать**.
3. **`differs_from_latest` = true** — есть изменения, перейти к Шагу 2.

### Шаг 2 — Получить diff (только для файлов с историей)

Вызови `localchanges` **строго без селекторов ревизий** (аналог `git diff`: сравнивает последнюю ревизию локальной истории с текущим состоянием):

```
project_name: ${project_name}
file_path: ${relative_file_path}
context_lines: 3
```

Если `has_changes` = false — изменений нет, завершить работу.

### Шаг 3 — Прочитать контекст

**ВАЖНО:** Diff показывает только **какие области** изменились, но не даёт достоверной информации о **точных номерах строк** и **содержимом строк** в текущей версии файла. Для получения истинных номеров строк и содержимого всегда используй результаты `read` — они отражают актуальное состояние файла. Diff служит только для определения диапазонов строк, которые нужно прочитать.

**Файл с историей (есть diff):** из hunk-заголовков `@@ -x,y +x,y @@` бери второй диапазон (`+x,y`) — положение в текущей версии. Для каждого hunk вызови `read` с запасом ±10 строк:

```
read:
path: ${absolute_file_path}
first_line: max(1, x - 10)
lines_number: y + 20
```

Перекрывающиеся с учётом запаса hunk-и объедини в один `read`.

**Новый файл (нет истории):** вызови `read` для всего файла. Это чтение целого файла переиспользуется на Шаге 5 — повторно файл не читать.

### Шаг 4 — Найти проблемы

**ВАЖНО:** При создании маркеров используй ТОЛЬКО данные из `read` — номера строк и содержимое должны соответствовать актуальному состоянию файла. Diff служит только для определения, какие строки нужно анализировать, но не для получения точного содержимого и номеров строк.

Файл с историей — анализируй только изменённые строки (`+` в diff), используя прочитанный контекст. Новый файл — весь файл.

**error** — блокирующие: закомментированный рабочий код; сломанная/недостижимая логика; незакрытая транзакция (`НачатьТранзакцию` без фиксации/отмены по всем веткам); прямое обращение к БД в цикле (запрос, `ПолучитьОбъект`, чтение реквизита ссылки на каждой итерации).

**warning** — потенциальные: временный/тестовый код по намерению (`a`, `b`, `tmp`, `test`, `xxx`, отладочные `Сообщить`); избыточная/тавтологичная логика; жёстко заданные строки метаданных вместо констант (`"Справочник.Номенклатура"` в коде); отсутствие проверки результата (`Найти`/`Получить` вернул `Неопределено`, значение используется без проверки); синхронный вызов там, где нужен асинхронный (`ОткрытьФорму`/`ПоказатьВопрос` без продолжения); метод делает несколько несвязанных вещей (декомпозиция по смыслу, не по числу строк).

**info** — смысловые: имя переменной/метода расходится с назначением; магическое число/строка, смысл которых неочевиден из контекста.

По каждой находке собери поля **под именами, которые примет `setmarkers`**:

- `marker_line` — номер строки (для нового файла — абсолютный номер в файле)
- `marker_highlighted_text` — проблемный фрагмент. **Бери достаточно широким, чтобы он был уникален в файле** (проблемная строка плюс строка контекста, если сама по себе строка повторяется) — сверка маркеров идёт по тексту, и неуникальный фрагмент собьёт снятие
- `severity` — `error`, `warning` или `info`
- `message` — описание проблемы
- Только для `error` и `warning`: положи в маркер quick-fix с быстрой правкой. Маркеры `info` quick-fix не заполняется.

### Шаг 5 — Прочитать фактическое состояние файла для сверки

Нужно полное содержимое файла, чтобы сверить маркеры с реальным кодом, а не только с diff.

- **Новый файл:** уже прочитано на Шаге 4 — переиспользуй, повторно не читай.
- **Файл с историей:** вызови `read` для всего файла.

### Шаг 6 — Обновить маркеры

Используйте SetMarkers для создания маркеров в файлах. Для ai_marker (ошибки/проблемы) укажите:

**Обязательные параметры:**
- `type`: "ai_marker" (или опустить, если есть severity)
- `path`: **АБСОЛЮТНЫЙ** путь к файлу (например: "C:/Projects/MyProject/src/Module.bsl")
- `message`: описание проблемы
- `marker_line`: номер строки (1-based)
- `marker_highlighted_text`: **минимальный** фрагмент кода (без лишнего контекста)

**Обязательные для ai_marker:**
- `action_prompt`: промпт для исправления
- `action_title`: короткое название действия  
- `action_description`: детальное описание действия

**Рекомендуемые для ai_marker:**
- `severity`: "error" | "warning" | "info"
- `priority`: "high" | "normal" | "low"

**Пример:**
```json
{
  "type": "ai_marker",
  "path": "C:/Projects/MyProject/src/CommonModules/Module.bsl",
  "message": "Использование устаревшего метода",
  "marker_line": 42,
  "marker_highlighted_text": "УстаревшийМетод()",
  "action_prompt": "Заменить УстаревшийМетод() на НовыйМетод()",
  "action_title": "Заменить метод",
  "action_description": "Использовать НовыйМетод() вместо устаревшего",
  "severity": "warning",
  "priority": "normal"
}

**ВАЖНО:** Поля `marker_line` и `marker_highlighted_text` в маркерах должны **точно соответствовать** содержимому, полученному из `read` в Шаге 5. Любое несоответствие приведет к ошибке "Target content not found in line X" или "marker_line must be a positive integer".

Вызывай тулы только если есть что менять.
**`setmarkers`** — одним вызовом все новые проблемы.
Нет новых проблем — `setmarkers` не вызывать.

**ВАЖНО**: Итоговое сообщение выводи как plain text, без форматирования. Кратко: сколько маркеров поставлено или не поставлено.
