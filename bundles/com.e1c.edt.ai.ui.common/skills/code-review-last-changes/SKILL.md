# Code Review незакоммиченных изменений (1C EDT)
 
Второй слой поверх штатного статического анализатора EDT. Задача — находить то, что правилом не закодируешь: смысловые проблемы, антипаттерны, потенциальные баги. **Не помечай то, что уже ловит штатный статический анализатор EDT или форматтер** — только то, что вне их охвата. Для tracked-файлов находка обязана сидеть на изменённой строке; для untracked изменёнными считаются все строки файла.
 
Наличие git-репозитория гарантируется вызывающей стороной — этот скилл вызывается только для файлов под git. Отдельно проверять наличие репозитория не нужно.
 
## Входные параметры
 
| Параметр | Описание |
|----------|----------|
| `${project_name}` | Имя проекта в EDT |
| `${file_path}` | Абсолютный путь к файлу для ревью |
 
## Порядок работы
 
Для получения данных используй **только** тулы из этого скилла. Не используй другие git-команды и не обращайся к файловой системе в обход `read`.
 
### Шаг 1 — Определить статус файла
 
Вызови `jgit`:
 
```
args: ["status", "--porcelain", "--", "<путь_к_файлу_относительно_корня_репозитория>"]
working_directory: <корень_репозитория>
```
 
`${file_path}` абсолютный — преобразуй его в путь относительно корня репозитория.
 
**Обработка статуса:**
 
1. **Пустой статус** (нет вывода) — файл не изменён относительно HEAD. Немедленно завершить работу, маркеры не трогать.
2. **Untracked** (`??` в начале строки) — файл новый, ещё ни разу не закоммичен. Пропустить Шаг 2 (diff не нужен), в Шаге 4 прочитать файл целиком и ревьюить как «всё добавлено».
3. **Модификация** (`M`, `M `, `A`, `AM`, `MM` и т.п.) — перейти к Шагу 2.
### Шаг 2 — Получить diff (только для tracked-файлов)
 
```
args: ["diff", "HEAD", "--", "<путь_к_файлу_относительно_корня_репозитория>"]
working_directory: <корень_репозитория>
```
 
**Пустой diff** — немедленно завершить работу, маркеры не трогать.
 
### Шаг 3 — Получить текущие маркеры
 
```
getmarkers:
project_name: ${project_name}
path: ${file_path}
marker_type: "ai_marker"
```
 
### Шаг 4 — Прочитать контекст
 
**Tracked (есть diff):** из hunk-заголовков `@@ -x,y +x,y @@` бери второй диапазон (`+x,y`) — положение в текущей версии. Для каждого hunk вызови `read` с запасом ±10 строк:
 
```
read:
path: ${file_path}
first_line: max(1, x - 10)
lines_number: y + 20
```
 
Перекрывающиеся с учётом запаса hunk-и объедини в один `read`.
 
**Untracked (нет diff):** вызови `read` для всего файла:
 
```
read:
path: ${file_path}
```
 
Это чтение целого файла переиспользуется на Шаге 6 — повторно файл не читать.
 
### Шаг 5 — Найти проблемы
 
Tracked — анализируй только изменённые строки (`+` в diff), используя прочитанный контекст. Untracked — весь файл. Не помечай то, что в охвате штатного анализатора (нарушения правил, неиспользуемые переменные/параметры, директивы компиляции, устаревшие методы, форматирование).
 
**error** — блокирующие: закомментированный рабочий код; сломанная/недостижимая логика; незакрытая транзакция (`НачатьТранзакцию` без фиксации/отмены по всем веткам); прямое обращение к БД в цикле (запрос, `ПолучитьОбъект`, чтение реквизита ссылки на каждой итерации).
 
**warning** — потенциальные: временный/тестовый код по намерению (`a`, `b`, `tmp`, `test`, `xxx`, отладочные `Сообщить`); избыточная/тавтологичная логика; жёстко заданные строки метаданных вместо констант (`"Справочник.Номенклатура"` в коде); отсутствие проверки результата (`Найти`/`Получить` вернул `Неопределено`, значение используется без проверки); синхронный вызов там, где нужен асинхронный (`ОткрытьФорму`/`ПоказатьВопрос` без продолжения); метод делает несколько несвязанных вещей (декомпозиция по смыслу, не по числу строк).
 
**info** — смысловые: имя переменной/метода расходится с назначением; магическое число/строка, смысл которых неочевиден из контекста.
 
По каждой находке собери поля **под именами, которые примет `setmarkers`**:
 
- `marker_line` — номер строки (для untracked — абсолютный номер в файле)
- `marker_highlighted_text` — проблемный фрагмент. **Бери достаточно широким, чтобы он был уникален в файле** (проблемная строка плюс строка контекста, если сама по себе строка повторяется) — сверка маркеров идёт по тексту, и неуникальный фрагмент собьёт снятие
- `severity` — `error`, `warning` или `info`
- `message` — описание проблемы
- Только для `error` и `warning`: `action_title` (3–5 слов), `action_description`, `action_prompt`. Для `info` quick-fix не заполняется.
### Шаг 6 — Прочитать фактическое состояние файла для сверки
 
Нужно полное содержимое файла на диске, чтобы сверить маркеры с реальным кодом, а не только с diff.
 
- **Untracked:** уже прочитано на Шаге 4 — переиспользуй, повторно не читай.
- **Tracked:** вызови `read` для всего файла:
```
read:
path: ${file_path}
```
 
### Шаг 7 — Сверить с существующими маркерами
 
Для каждого маркера из `getmarkers` проверь, присутствует ли его `marker_highlighted_text` в **фактическом состоянии файла из Шага 6**:
 
- **Текст присутствует** — проблема не исправлена, маркер оставить.
- **Текст отсутствует** — проблема исправлена, маркер удалить.
- **Новая проблема, маркера нет** — добавить.
Ориентируйся на текст фрагмента, а не на номер строки: при правках выше по файлу строки сдвигаются.
 
**Важно:** сверка идёт по фактическому состоянию файла (Шаг 6), а НЕ по присутствию в текущем diff. Иначе после коммита HEAD сдвигается, закоммиченный код выпадает из diff против нового HEAD, и маркеры зависают сиротами.
 
### Шаг 8 — Обновить маркеры
 
Вызывай тулы только если есть что менять.
 
**`deletemarkers`** — id только тех маркеров, чьи проблемы исправлены. Нет устаревших — не вызывать.
 
**`setmarkers`** — одним вызовом все новые проблемы:
 
```
setmarkers:
project_name: ${project_name}
markers[]:
    type: "ai_marker"
    path: ${file_path}
    marker_line: <marker_line из Шага 5>
    marker_highlighted_text: <marker_highlighted_text из Шага 5>
    message: <message>
    severity: error | warning | info
    action_prompt: <...> # только error/warning
    action_title: <...> # только error/warning
    action_description: <...> # только error/warning
```
 
Нет новых проблем — `setmarkers` не вызывать.
