# Code Review последних изменений (1C EDT)

## Входные параметры

| Параметр | Описание |
|----------|----------|
| `${project_name}` | Имя проекта в EDT |
| `${file_path}` | Абсолютный путь к файлу для ревью |

## Препроцессинг
`localchangs`:
!tool('localchanges')

`getmarkers`:
!tool('getmarkers')

## Анализ

### Шаг 1 — Проверить наличие изменений в препроцессинге

Если `localchanges` не содержит diff (`has_changes: false`) — **немедленно завершить работу, маркеры не трогать** (не вызывай тул localchanges, используй полученные данные из препроцессинга). 

Для получения дополнительных данных использовать **только** тулы из этого скилла. Не использовать git, jgit или другие инструменты.

### Шаг 2 — Прочитать контекст вокруг изменений

Из результата `localchanges` извлеки hunk-заголовки вида `@@ -x,y +x,y @@`.
Второй диапазон (`+x,y`) описывает положение в текущей версии файла: `x` — номер первой строки, `y` — количество строк.

Для каждого hunk вызови `read` с запасом ±10 строк:
```
path: ${file_path}
from_line: max(1, x - 10)
line_count: y + 20
```

Если несколько hunk-ов перекрываются с учётом запаса — объедини их в один вызов `read`.

### Шаг 3 — Найти проблемы

Анализируй только изменённые строки из diff, используй прочитанный контекст для понимания окружения и точного определения номеров строк.

**error** — блокирующие проблемы:
- Закомментированный рабочий код (не удалён, а закомментирован)
- Сломанная или недостижимая логика
- Обращение к неопределённым переменным или реквизитам
- Отсутствие обязательной директивы компилятора (`&НаКлиенте`, `&НаСервере` и т.д.)
- Прямое обращение к БД (запросы, `ПолучитьОбъект`) внутри цикла
- Использование синхронных вызовов там, где требуется асинхронный (`ОткрытьФорму` без обработчика)
- Незакрытые транзакции (`НачатьТранзакцию` без `ЗафиксироватьТранзакцию`/`ОтменитьТранзакцию`)

**warning** — потенциальные проблемы:
- Временный или тестовый код (переменные `a`, `b`, `tmp`, `test`, `xxx` и т.п.)
- Неиспользуемые переменные или параметры
- Избыточная или тавтологичная логика (условие всегда истинно/ложно)
- Жёстко заданные строки вместо констант или параметров (`"Справочник.Номенклатура"` прямо в коде)
- Использование устаревших методов (`Предупреждение`, `Вопрос` вместо асинхронных аналогов)
- Отсутствие проверки результата перед использованием (`Найти`, `Получить`)
- Длинные процедуры (более 80 строк) без декомпозиции

**info** — стилевые и прочие замечания:
- Неиспользуемые параметры процедуры/функции
- Отсутствие комментария к процедуре/функции
- Нарушение соглашений об именовании (латиница в именах переменных, однобуквенные имена)
- Отсутствие пустой строки в конце файла

### Шаг 4 — Сравнить с существующими маркерами

Для каждого маркера из `getmarkers` проверь, присутствует ли `marker_highlighted_text` в текущем коде на той же строке:

- **Текст всё ещё присутствует** — проблема не исправлена, маркер оставить без изменений
- **Текст отсутствует** — проблема исправлена, маркер удалить
- **Новая проблема найдена и такого маркера нет** — маркер добавить

## Обновление маркеров

Вызови тулы только если есть что менять:

**Удалить устаревшие маркеры** — вызови `deletemarkers` передав id только тех маркеров, чьи проблемы исправлены. Не удалять маркеры у которых проблема осталась.

**Добавить новые маркеры** — вызови `setmarkers` одним вызовом для всех новых проблем:

```
project_name: ${project_name}
markers[]:
  type: "ai_marker"
  path: ${file_path}
  marker_line: <номер строки — из пронумерованного ответа read>
  marker_highlighted_text: <фрагмент кода — одна или несколько строк>
  message: <описание проблемы — что именно не так>
  severity: error | warning | info
  action_prompt: <инструкция для агента по исправлению>     # для error и warning
  action_title: <краткое название действия, 3–5 слов>        # для error и warning
  action_description: <что конкретно нужно сделать>          # для error и warning
```

Если новых проблем нет — `setmarkers` не вызывать.
Если устаревших маркеров нет — `deletemarkers` не вызывать.
