Ревью изменений кода 1С перед коммитом: анализ диффов с учётом специфики платформы 1С:Предприятие, стандартов разработки и типовых ошибок.
  
## Препроцессинг
 
Текущие индексированные изменения перед коммитом:
 
```
!tool('git_diff')
```

Используй переданные данные препроцессинга для анализа по правилам, описанным далее.

---

## Подготовка к анализу

Для кеорректного определения номеров строк используй mcp-tool `read` для чтения файлов, участвующих в `diff`. Указывай валидные номера строк и отступы в ссылках на расположение.
Правильное оформление ссылки выглядит так.

1. Для позиции:
```
edt-file://нормализованный_путь:строка:колонка
```
2. Для диапазона:
```
edt-file://нормализованный_путь:строка:колонка:последняя_строка:последняя_колонка
```

### Пример ссылки:
```
edt-file://C:/Projects/MyProject/src/Module.bsl:10:5:20:15
```
Это ссылка на диапазон от строки 10, колонка 5 до строки 20, колонка 15.

### Если проблема в середине строки
Если проблема в середине строки с номером `x`, то корректно считай отступы и создавай ссылку по примеру: `x:старт:x:финиш`.

### Если нужно просто выделить диапазон строк
Если нужно просто выделить диапазон строк от `x` до `y`, то используй такой шаблон: `x:0:y:0`.

## Конвертация путей файлов
 
Перед выводом конвертируй технические пути файлов в читаемый вид: разделители `/` заменяй на ` → `, а служебные имена папок и файлов EDT/Конфигуратора переводи на русский по таблице ниже.
 
Пример: `ВыгрузкаОтчётов/Forms/Форма/Module.bsl` -> `ВыгрузкаОтчётов → Формы → Форма → Модуль`
 
| Сегмент пути | Читаемый вид |
|---|---|
| `Forms` | Формы |
| `Module.bsl` | Модуль |
| `ObjectModule.bsl` | Модуль объекта |
| `ManagerModule.bsl` | Модуль менеджера |
| `ManagedApplicationModule.bsl` | Модуль управляемого приложения |
| `SessionModule.bsl` | Модуль сеанса |
| `CommandModule.bsl` | Модуль команды |
| `Form.bsl` / `Module` (в папке формы) | Модуль |
| `Templates` | Макеты |
| `Commands` | Команды |
| `Recordsets` | Наборы записей |
| `Ext` | (опускается) |
| `.mdo` (расширение) | (опускается, остаётся имя объекта) |
 
Имена прикладных объектов (`ВыгрузкаОтчётов`, `Форма`, `Контрагенты` и т.п.) сохраняй как есть. Расширения файлов в итоговом пути не показывай.

## Области ревью
 
### 1. Архитектура и структура
 
- Соответствие объектов конфигурации их назначению (Документ, Справочник, Регистр и т.д.)
- Корректное размещение бизнес-логики: клиент / сервер / &НаСервере / &НаКлиенте / &НаСервереБезКонтекста
- Отсутствие бизнес-логики в модуле формы там, где она должна быть в общем модуле
- Правильное использование расширений конфигурации (если применимо)
### 2. Производительность
 
- Запросы внутри циклов (антипаттерн «запрос в цикле»)
- Отсутствие отбора в запросах — выборка «всего» без условий
- Использование `ПолучитьОбщийМодуль` или устаревших конструкций вместо актуальных
- Избыточные вызовы сервера из клиентского кода
- Неиндексированные поля в условиях запросов (рекомендательно)
- Использование `НайтиПоНаименованию` вместо поиска по коду или ссылке
### 3. Корректность
 
- Незакрытые транзакции (`НачатьТранзакцию` без `ЗафиксироватьТранзакцию` / `ОтменитьТранзакцию`)
- Отсутствие обработки исключений вокруг `ЗаписатьОбъект`, `Записать` в критичных местах
- Некорректное использование блокировок (`УстановитьБлокировку` без снятия)
- Запись объектов без `ОбменДанными.Загрузка = Истина` там, где это требуется
- Использование устаревших методов платформы (например, `ОткрытьФорму` вместо `ОткрытьФормуМодально`)
- Некорректная работа с датами (пустая дата `'00010101'`, часовые пояса)
### 4. Безопасность
 
- Привилегированный режим (`УстановитьПривилегированныйРежим(Истина)`) без обоснования
- Динамические запросы через конкатенацию строк (риск инъекций)
- Передача паролей или токенов в открытом виде в коде или параметрах
- Права доступа: проверка прав перед операциями (РольДоступна, ПравоДоступа)
### 5. Стиль и стандарты 1С
 
- Именование переменных, процедур и функций: ВерблюжийРегистр, на русском языке
- Отсутствие закомментированного кода
- Длина процедур/функций: предпочтительно до 50–80 строк
- Наличие комментариев для нетривиальной логики
- Использование `// TODO:` / `// FIXME:` без трекера задачи
- Параметры функций: не более 7, использование структур если больше
- Явное указание `Экспорт` только там, где метод действительно публичный
### 6. Типовые антипаттерны 1С
 
| Антипаттерн | Описание |
|---|---|
| Запрос в цикле | `Выполнить()` внутри `Для Каждого ... Цикл` |
| Хардкод ссылок | `Справочники.Валюты.НайтиПоКоду("RUB")` в модуле без параметризации |
| Глобальные переменные | Переменные уровня модуля вместо параметров |
| Работа с числом без типа | Числа без явного указания разрядности там, где важна точность |
| Отсутствие проверки `Не ЗначениеЗаполнено` | Работа с реквизитом без проверки перед обращением |

## Формат вывода
 
Замечания оформляй списком, а не таблицей. Каждый пункт списка — отдельное замечание со следующей структурой:
 
- **Расположение** — ссылка на место в коде. Оформляй как ССЫЛКУ (Link) на место в коде. Используй указания по номерам строк и отступам, указанным в пункте `Подготовка к анализу`.
- **Серьёзность / Категория** — словом (Критично / Высокая / Средняя / Низкая; либо категория для рекомендаций: Производительность, Стиль, Безопасность и т.д.).
- **Замечание** — в чём проблема.
- **Решение** — конкретное предложение по улучшению: что и как изменить, по возможности с фрагментом кода. Если фрагмент больше 3 строк, оставить только текстовую рекомендацию.  

Пример вывода:
 
```markdown
## Ревью изменений
 
### Итог
[1–2 предложения: общая оценка изменений и их влияния на конфигурацию]
 
### Замечания
 
1. **Расположение:** Конфигурация→Обработки→ВыгрузкаОтчётов→Команды→ВыгрузитьОтчёты:120
- **Серьёзность:** Критично
- **Замечание:** Запрос выполняется внутри цикла `Для Каждного ... Цикл`, что приводит к деградации производительности на больших выборках.
- **Решение:** Вынести запрос за пределы цикла, получив все данные одним запросом с отбором по нужным ссылкам, и работать с результатом через `Выбрать()` или загрузку в соответствие.
 
2. **Расположение:** Конфигурация→Обработки→ВыгрузкаОтчётов→Формы→Форма:64-68
- **Серьёзность:** Высокая
- **Замечание:** Открыта транзакция `НачатьТранзакцию()` без гарантированной фиксации/отмены в блоке `Попытка ... Исключение`.
- **Решение:** Обернуть тело транзакции в `Попытка`, в `Исключение` вызвать `ОтменитьТранзакцию()` и пробросить ошибку через `ВызватьИсключение`.
 
### Что сделано хорошо
- [Позитивные наблюдения]
 
### Вердикт
[Можно коммитить / Доработать / Требует обсуждения] (кратко опиши что требует доработки).
 
**Провести исправления согласно предложенным решениям?**
```

## Завершающий шаг — предложение исправлений
 
После вывода ревью задай пользователю вопрос:
 
**Провести исправления согласно предложенным решениям?**

Используй mcp-tool для предоставления выбора (да/нет/вариант от пользователя). Если "да", то выведи список проблем и попроси пользователя отметить те, которые нужно исправить. И далее, для каждой ошибки предоставляй выбор как править: как указано в "Решении" или как напишет пользователь.
 
Если пользователь отказывается — заверши работу, ничего не изменяя.
