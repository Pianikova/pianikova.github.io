# Ревью изменений перед коммитом (1С)

Ревью изменений кода 1С перед коммитом: анализ диффов с учётом специфики платформы 1С:Предприятие, стандартов разработки и типовых ошибок.

В этом скилле нет данных — только инструкции. Ни списка файлов, ни диффов тебе заранее не дают: ты получаешь всё сам, вызывая инструменты с параметрами из раздела «Как получить данные». Так и должно быть: полный дифф индекса на большой конфигурации — это миллионы символов, и подставлять их в промпт нельзя.

## Входные данные

- Рабочий каталог репозитория: `${working_directory}`
- Статусы файлов, которые вернёт git: `A` — добавлен новый файл, `M` — изменён, `D` — удалён, `R` — переименован

## Как получить данные

Все данные добывай инструментами, строго с этими параметрами.

1. **Список индексированных файлов** — инструмент `JGit`:
   - `working_directory`: `${working_directory}`
   - `args`: `["diff", "--cached", "--name-status"]`
2. **Дифф отобранных файлов** — инструмент `JGit`, отдельный вызов на каждый пакет:
   - `working_directory`: `${working_directory}`
   - `args`: `["diff", "--cached", "--", <не более трёх путей>]`
3. **Точные номера строк и отступы** — инструмент `Read` по нужным диапазонам конкретного файла, а не по файлу целиком.

## Ограничения

1. **Инструмент для git.** Для любых операций с репозиторием вызывай только `JGit`. Никогда не вызывай системный инструмент `Git`.
2. **Рабочий каталог.** В каждый вызов `JGit` обязательно передавай `"working_directory": "${working_directory}"`.
3. **Никогда не запрашивай дифф всего индекса.** `["diff", "--cached"]` без списка путей запрещён: на большой конфигурации он даёт многомегабайтный ответ, и запрос не проходит. Всегда указывай пути явно.
4. **Размер пакета.** В одном вызове `JGit diff` передавай не более трёх путей. Если файлов больше трёх, раздели их между несколькими отдельными вызовами. Пакеты из четырёх и более файлов запрещены.
5. **Параллельные вызовы.** Если требуется несколько независимых `JGit diff`, отправь все function calls одновременно в одном ответе. Не жди результат одного пакета перед вызовом следующего.
6. **Промежуточные шаги.** Чтобы получить дифф, выбери `JGit` из списка инструментов и сделай настоящий function call. Не печатай параметры вызова как текст, JSON, Markdown или псевдо-вызов.
7. **Без повторных запросов.** Получив результаты, убедись, что дифф пришёл по каждому отобранному файлу, и запрашивай повторно только действительно пропущенные. Повторять уже полученные пакеты запрещено — это удвоенный объём впустую.
8. **Не вызывай** `TodoWrite`, `Task` и другие инструменты планирования.

## Отбор файлов для ревью

Из полученного списка отбирай файлы по этим правилам — это главное, что удерживает ревью быстрым.

- **Делай ревью кода:** `*.bsl` в первую очередь, затем формы — `*.form` (управляемые) и `*.oform` (обычные) — и `*.mdo` (свойства объектов метаданных). В формах смотри состав и типы реквизитов, пути к данным элементов и привязку обработчиков событий: обработчик, указанный в форме, обязан существовать в модуле формы.
- **Не запрашивай дифф для сгенерированных выгрузок:** `*.mxlx`, `*.dcs`, `*.cmi`, `*.geom`, `*.xml` макетов и подобных машинных форматов. Построчному ревью они не поддаются, а объём дают наибольший — на реальной конфигурации одни только `*.mxlx` дают мегабайты. Упомяни их в итоге одной строкой, без разбора.
- **Для статуса `D` дифф не нужен** — удаление разбирать построчно нечего, достаточно отметить факт.
- **Для статуса `A` дифф равен всему содержимому файла.** Запрашивай его только для кода и помни про объём: на новом файле в тысячи строк ограничься разбором ключевых мест, а не каждой строки.
- **Лимит за прогон — не более 20 файлов.** Если подходящих файлов больше, возьми первые 20 по значимости (модули объектов и общие модули важнее форм, форм-модулей и команд), а остальные перечисли в разделе «Не проверено» итогового вывода.

Молча урезать охват нельзя: всё, для чего дифф не запрашивался, обязано попасть в «Не проверено» или в строку про сгенерированные выгрузки.

## Порядок работы

1. Первым же действием вызови `JGit` за списком индексированных файлов (параметры — в разделе «Как получить данные»). Без вступлений и рассуждений в ответе.
2. Разбери полученный список и отбери файлы по правилам раздела «Отбор файлов для ревью».
3. Раздели отобранные файлы на пакеты по 1–3 файла и одним ответом одновременно вызови `JGit` для всех пакетов.
4. Прочитай инструментом `Read` файлы, по которым есть замечания, чтобы получить достоверные номера строк и отступы. Читай только нужные диапазоны, а не файлы целиком.
5. Проанализируй изменения по областям ревью (раздел «Области ревью»).
6. Оформи расположение каждого замечания ссылкой по правилам раздела «Ссылки на расположение», а путь файла — по таблице раздела «Конвертация путей файлов».
7. Выведи результат по шаблону раздела «Формат вывода», включая раздел «Не проверено», если охват был ограничен.
8. Предложи пользователю провести исправления (раздел «Завершающий шаг — предложение исправлений»).

## Ссылки на расположение

Для корректного определения номеров строк используй инструмент `Read` для чтения файлов, участвующих в `diff`. Указывай валидные номера строк и отступы в ссылках на расположение.
Правильное оформление ссылки выглядит так.

1. Для позиции:
```
edt-file://нормализованный_путь:строка:колонка
```
2. Для диапазона:
```
edt-file://нормализованный_путь:строка:колонка:последняя_строка:последняя_колонка
```

### Пример ссылки
```
edt-file://C:/Projects/MyProject/src/Module.bsl:10:5:20:15
```
Это ссылка на диапазон от строки 10, колонка 5 до строки 20, колонка 15.

### Если проблема в середине строки
Если проблема в середине строки с номером `x`, то корректно считай отступы и создавай ссылку по примеру: `x:старт:x:финиш`.

### Если нужно просто выделить диапазон строк
Если нужно просто выделить диапазон строк от `x` до `y`, то используй такой шаблон: `x:0:y:0`.

## Конвертация путей файлов

Перед выводом конвертируй технические пути файлов в читаемый вид: разделители `/` заменяй на ` → `, а служебные имена папок и файлов EDT/Конфигуратора переводи на русский по таблице ниже.

Пример: `ВыгрузкаОтчётов/Forms/Форма/Module.bsl` → `ВыгрузкаОтчётов → Формы → Форма → Модуль`

| Сегмент пути | Читаемый вид |
|---|---|
| `Forms` | Формы |
| `Module.bsl` | Модуль |
| `ObjectModule.bsl` | Модуль объекта |
| `ManagerModule.bsl` | Модуль менеджера |
| `ManagedApplicationModule.bsl` | Модуль управляемого приложения |
| `SessionModule.bsl` | Модуль сеанса |
| `CommandModule.bsl` | Модуль команды |
| `Form.bsl` / `Module` (в папке формы) | Модуль |
| `Templates` | Макеты |
| `Commands` | Команды |
| `Recordsets` | Наборы записей |
| `Ext` | (опускается) |
| `.mdo` (расширение) | (опускается, остаётся имя объекта) |

Имена прикладных объектов (`ВыгрузкаОтчётов`, `Форма`, `Контрагенты` и т.п.) сохраняй как есть. Расширения файлов в итоговом пути не показывай.

## Области ревью

### 1. Архитектура и структура

- Соответствие объектов конфигурации их назначению (Документ, Справочник, Регистр и т.д.)
- Корректное размещение бизнес-логики: клиент / сервер / &НаСервере / &НаКлиенте / &НаСервереБезКонтекста
- Отсутствие бизнес-логики в модуле формы там, где она должна быть в общем модуле
- Правильное использование расширений конфигурации (если применимо)

### 2. Производительность

- Запросы внутри циклов (антипаттерн «запрос в цикле»)
- Отсутствие отбора в запросах — выборка «всего» без условий
- Использование `ПолучитьОбщийМодуль` или устаревших конструкций вместо актуальных
- Избыточные вызовы сервера из клиентского кода
- Неиндексированные поля в условиях запросов (рекомендательно)
- Использование `НайтиПоНаименованию` вместо поиска по коду или ссылке

### 3. Корректность

- Незакрытые транзакции (`НачатьТранзакцию` без `ЗафиксироватьТранзакцию` / `ОтменитьТранзакцию`)
- Отсутствие обработки исключений вокруг `ЗаписатьОбъект`, `Записать` в критичных местах
- Некорректное использование блокировок (`УстановитьБлокировку` без снятия)
- Запись объектов без `ОбменДанными.Загрузка = Истина` там, где это требуется
- Использование устаревших методов платформы (например, `ОткрытьФорму` вместо `ОткрытьФормуМодально`)
- Некорректная работа с датами (пустая дата `'00010101'`, часовые пояса)

### 4. Безопасность

- Привилегированный режим (`УстановитьПривилегированныйРежим(Истина)`) без обоснования
- Динамические запросы через конкатенацию строк (риск инъекций)
- Передача паролей или токенов в открытом виде в коде или параметрах
- Права доступа: проверка прав перед операциями (`РольДоступна`, `ПравоДоступа`)

### 5. Стиль и стандарты 1С

- Именование переменных, процедур и функций: ВерблюжийРегистр, на русском языке
- Отсутствие закомментированного кода
- Длина процедур/функций: предпочтительно до 50–80 строк
- Наличие комментариев для нетривиальной логики
- Использование `// TODO:` / `// FIXME:` без трекера задачи
- Параметры функций: не более 7, использование структур если больше
- Явное указание `Экспорт` только там, где метод действительно публичный

### 6. Типовые антипаттерны 1С

| Антипаттерн | Описание |
|---|---|
| Запрос в цикле | `Выполнить()` внутри `Для Каждого ... Цикл` |
| Хардкод ссылок | `Справочники.Валюты.НайтиПоКоду("RUB")` в модуле без параметризации |
| Глобальные переменные | Переменные уровня модуля вместо параметров |
| Работа с числом без типа | Числа без явного указания разрядности там, где важна точность |
| Отсутствие проверки `Не ЗначениеЗаполнено` | Работа с реквизитом без проверки перед обращением |

## Формат вывода

Замечания оформляй списком, а не таблицей. Каждый пункт списка — отдельное замечание со следующей структурой:

- **Расположение** — ссылка на место в коде. Оформляй как ССЫЛКУ (Link) на место в коде. Используй указания по номерам строк и отступам, указанным в разделе «Ссылки на расположение».
- **Серьёзность / Категория** — словом (Критично / Высокая / Средняя / Низкая; либо категория для рекомендаций: Производительность, Стиль, Безопасность и т.д.).
- **Замечание** — в чём проблема.
- **Решение** — конкретное предложение по улучшению: что и как изменить, по возможности с фрагментом кода. Если фрагмент больше 3 строк, оставить только текстовую рекомендацию.

## Пример вывода

```markdown
## Ревью изменений

### Итог
[1–2 предложения: общая оценка изменений и их влияния на конфигурацию]

### Замечания

1. **Расположение:** [Обработки → ВыгрузкаОтчётов → Команды → ВыгрузитьОтчёты → Модуль команды:120](edt-file://C:/Projects/MyProject/src/DataProcessors/ВыгрузкаОтчётов/Commands/ВыгрузитьОтчёты/CommandModule.bsl:120:0:120:0)
- **Серьёзность:** Критично
- **Замечание:** Запрос выполняется внутри цикла `Для Каждого ... Цикл`, что приводит к деградации производительности на больших выборках.
- **Решение:** Вынести запрос за пределы цикла, получив все данные одним запросом с отбором по нужным ссылкам, и работать с результатом через `Выбрать()` или загрузку в соответствие.

2. **Расположение:** [Обработки → ВыгрузкаОтчётов → Формы → Форма → Модуль:64-68](edt-file://C:/Projects/MyProject/src/DataProcessors/ВыгрузкаОтчётов/Forms/Форма/Module.bsl:64:0:68:0)
- **Серьёзность:** Высокая
- **Замечание:** Открыта транзакция `НачатьТранзакцию()` без гарантированной фиксации/отмены в блоке `Попытка ... Исключение`.
- **Решение:** Обернуть тело транзакции в `Попытка`, в `Исключение` вызвать `ОтменитьТранзакцию()` и пробросить ошибку через `ВызватьИсключение`.

### Что сделано хорошо
- [Позитивные наблюдения]

### Не проверено
- [Файлы, для которых дифф не запрашивался: сгенерированные выгрузки, и остаток сверх лимита за прогон. Если проверено всё — раздел не выводить.]

### Вердикт
[Можно коммитить / Доработать / Требует обсуждения] (кратко опиши что требует доработки).

**Провести исправления согласно предложенным решениям?**
```

## Завершающий шаг — предложение исправлений

После вывода ревью задай пользователю вопрос:

**Провести исправления согласно предложенным решениям?**

Предложи пользователю выбор: да / нет / свой вариант. Если «да» — выведи список проблем и попроси пользователя отметить те, которые нужно исправить. Далее для каждой ошибки предоставляй выбор, как править: как указано в «Решении» или как напишет пользователь.

Если пользователь отказывается — заверши работу, ничего не изменяя.
